02 The bug that was hiding

Critical · fixed

Every browser document upload was being rejected with a 400.

The shared apiRequest() helper forced Content-Type: application/json onto all requests - including file uploads. A file upload has to carry a multipart boundary the browser sets itself; stamping JSON on top wiped that out, so the server couldn't read the file and threw it back. Schedule import, document processing - anything that sent a file - was broken for real users.

It slipped through because the only earlier test of that screen used a fake, canned response instead of a real upload, so the request never actually left the browser. My real-photo test is what exposed it. One-line-ish fix: don't stamp a content-type on file uploads, and let the browser do its job.

03 What I built - local AI, on a switch

Extraction now runs behind one setting, SCHEDULE_AI_PROVIDER. Flip it between fully-local and OpenAI whenever you like; nothing else changes.

photo / PDF / DOCX → Tesseract OCR → qwen2.5:7b (local) → editable preview → save
  • Free and private. Care-home schedules never leave the machine - no OpenAI key, no per-document cost, no expired-key surprises.
  • Nothing to decide again. It defaults to OpenAI if a key is set, otherwise local. Right now it's pinned to local because the key in .env is expired.
  • Every path covered. The quick importer, the background job queue, and the older document route all run through the same provider - no half-migrated corners.
  • Can't hog the server. OCR is capped so a flood of uploads can't pin the CPU; extras get a polite "busy, try again" instead of taking the box down.
