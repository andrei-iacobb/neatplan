Dashboard Per-Site Filter - Design Plan

Goal: the main dashboard currently aggregates every site into one view. Add a site selector so an OP or DIRECTOR can narrow the whole dashboard to one site, with a control that still works at 40+ sites.
Status: plan only, no code written. Branch feature/qr-nfc-checkin.
Observed live at http://localhost:4040 as admin@neatplan.com: two sites exist - Maple Care Home (55 rooms, 2 users) and Unassigned (site_legacy_backfill, 54 rooms, 4 users). The dashboard reports "109 Total Rooms", which is exactly the sum. That single number is the problem in miniature: it is half real data and half legacy backfill, and nothing on screen says so.

What actually feeds the dashboard

The dashboard is src/app/page.tsx (not a (dashboard)/page.tsx) rendering DashboardOverview from src/components/dashboard/dashboard-overview.tsx. All fetching happens client-side in one Promise.all at dashboard-overview.tsx:46-54. Seven endpoints, not the set assumed at kickoff:

EndpointAuthSite scoping todayCan the client filter it?
/api/usersrequireAdmin()siteScopeWhere (users/route.ts:21)Yes - returns siteId
/api/roomsrequireAuth()siteScopeWhere (rooms/route.ts:21)Yes - returns siteId

Three of the seven cannot be filtered in the browser at all. That settles the architecture: the filter is server-side. Doing rooms and users client-side while the weekly chart needs a round trip would leave two filtering mechanisms that drift apart.

Corrections to the brief. /api/metrics has no consumer anywhere in src/ - it is an ops endpoint, and its userSession and documentJob counts are not site-scoped at all (metrics/route.ts:18-19). /api/admin/compliance-rate, /api/admin/overdue-summary and /api/admin/completion-history feed the Audit page (src/app/(dashboard)/audit/page.tsx:110,139-140), not the dashboard. None of them need touching for this feature, though the same helper will serve them when Audit gets the same treatment.
Also: src/app/api/auth/switch-account/route.ts does not exist on disk despite appearing in git status, and there is no account or site switcher UI anywhere in the app.

1. Placement

Where the chrome actually is

There is no desktop topbar. The shell is a fixed 60px sidebar rail (src/components/ui/sidebar.tsx:119-226, expands to 220px on hover or pin) plus a content column at src/components/layout/conditional-layout.tsx:29-32. The only bar-shaped element is sidebar.tsx:229, which is md:hidden - mobile only, logo and hamburger. The sidebar never renders the signed-in user's name, role or site. The first element inside the content area is the dashboard's own <header> at dashboard-overview.tsx:121-134: greeting on the left, and on the right a static sentence, "Overview of your cleaning management system."

ForAgainst
Sits directly above everything it governs, so the scope-to-data relationship reads without explanation. Dashboard-only. Rooms and Equipment keep their own local pickers, so the same choice is made twice in a session.
Reclaims dead space. Nothing is displaced except a sentence that says nothing. The header is sm:flex-row; a wide control forces a rethink of the mobile stack.
Zero shell surgery - one component, one file, no layout regression risk on the other seven pages. Scrolls away with the page. Acceptable: the dashboard fits one viewport on large screens by design.

Option B - new global topbar in the shell

Add a persistent bar as a sibling above <main> in conditional-layout.tsx:29-32, hosting the site selector plus the user identity that the chrome currently never shows. Every page inherits one site context.

ForAgainst
One site context for the whole app. Rooms, Equipment, Schedule and Audit all obey it, and the two duplicated page-local pickers at rooms/page.tsx:333-344 and equipment/page.tsx:472-483 collapse into it. Builds a desktop topbar that does not exist today. Every page loses vertical space, and the dashboard's "fits one viewport" property (dashboard-overview.tsx:157 comment) is the first casualty.
Right long-term home for account switching and the missing profile menu. <main> carries pt-16 md:pt-6 to clear the mobile bar; a second bar means reworking that on mobile.
Sticky - survives scrolling on long pages. Global state that silently changes what six other pages show is a much larger blast radius to verify. Wrong first move.

Option C - inside the sidebar rail

Between the logo block (sidebar.tsx:129) and the nav list (sidebar.tsx:150). not recommended The rail is 60px collapsed and only expands on hover or when pinned, so the control would be an unlabelled icon most of the time. A dropdown anchored to a container that collapses out from under the cursor is a bad interaction, and site names would be permanently truncated.

Recommendation

Ship Option A. Build the control as a standalone src/components/dashboard/site-filter.tsx with the selection owned by a useSiteFilter() hook, so it is presentation-only and portable. If it earns its place, Option B is then a move of one JSX element plus lifting the hook - not a rewrite. Do not start with B: it changes six pages before anyone has confirmed the control is right.

2. Scaling

A fixed tab strip fails earlier than instinct suggests. The header's right slot is roughly 500px at the 1230px content width (dashboard-overview.tsx:119). At 13px in a pill with padding, "Maple Care Home" is about 130px and "All sites" about 85px. That is three real pills before it wraps into the greeting. The switch points below are set from that arithmetic, not from a round number.

Visible sitesControlWhy
0Nothing rendersFresh database, or a MANAGER with no siteId. /api/sites returns [] (sites/route.ts:24-26).
1Static chip showing the site name. Not interactive.A choice of one is not a choice. But the name still has to be on screen, otherwise the user cannot tell whether "109 rooms" is scoped. This is also what a MANAGER gets.
2 to 4Segmented pill row: All sites plus each name.Fits the slot, zero clicks to switch, whole option set visible. This is the "tab" Andrei asked for, and it is what today's data lands on.
5 to 10Single trigger button showing the current selection, opening a popover list.Past four pills the row wraps or truncates names to uselessness. The list is short enough that scanning beats typing, so no search box yet.
11 to 25Same popover, with a search input auto-focused on open. Type-to-filter on name and address.Above ten a list needs scrolling; typing three characters is faster than scrolling and reading.
26+Same popover and search, plus a pinned "Recent" group of the last three selections at the top, above a divider.At 40 sites nobody is choosing uniformly at random. Recency covers the common case; search covers the rest. Recents live in localStorage, so they cost nothing server-side.
200+Add windowed rendering to the list.Named for completeness. Not a real case for this product; do not build it speculatively.

Rules that hold at every count: All sites is always the first entry and always the default; Unassigned is always sorted last regardless of alphabetical order; the trigger always shows the current selection as text, never just an icon; keyboard support is arrow keys plus Enter plus Escape, and the trigger is a real <button> with aria-expanded. The pill row and the popover share one options array, so the switch between them is a render branch, not two implementations.

Why a hard count threshold rather than measuring overflow

Measuring the container and collapsing pills into a popover when they no longer fit is nicer and adapts to long site names. It also needs a ResizeObserver, a hidden measurement pass, and it makes the component's behaviour untestable without a real layout engine. Ship count thresholds first because they are predictable and unit-testable, then swap in measurement later behind the same props if long names turn out to be a real problem. The thresholds above already assume names as long as the ones in the live database.

3. Role behaviour

From src/lib/roles.ts: ROLE_RANK is OP:4, DIRECTOR:3, MANAGER:2, CLEANER:1 (roles.ts:16-21). canAccessAllSites is rank at or above DIRECTOR (roles.ts:45-47). isManagementRole is rank at or above MANAGER (roles.ts:40-42) and is what isAdmin encodes.

RoleReaches the dashboard?ControlWhat "All sites" means

DIRECTORYesFull control, identical to OPSame as OP. canAccessAllSites does not distinguish them.

Rendering rule, in order: if the user is not canAccessAllSites, render the static chip and stop. Else if sites.length < 2, render the static chip (or nothing at zero). Else render the interactive control at the size band from section 2. The chip for a MANAGER is a genuine improvement independent of this feature - right now nothing in the chrome tells a MANAGER which site they are looking at.

Pre-existing bug worth logging separately. prisma/schema.prisma:340-346 defines enum UserRole { OWNER, OP, DIRECTOR, MANAGER, CLEANER }, but roles.ts:11 omits OWNER. roleRank falls through to ?? 0 (roles.ts:30-32), so an OWNER ranks below CLEANER, gets isAdmin === false, and is redirected to /clean. Not caused by this work and not fixed by it, but any role-shaped change should not paper over it.

4. State and URL

Selection lives in the URL query param ?site=<siteId>, with localStorage['neatplan-dashboard-site'] as the sticky default. Absent or site=all means all sites.

Resolution order on mount: URL param, then localStorage, then all. Whichever wins is validated against the fetched /api/sites list before it is applied - a stale id must never silently produce an empty dashboard (see section 6).

OptionVerdict
URL query paramPrimary. Deep-linkable, so "look at Maple's overdue count" is a link not a set of instructions. Survives refresh. Two tabs can hold two different sites. Screenshots carry their own context.
localStorageSecondary, for stickiness only. Key neatplan-dashboard-site, matching the existing convention (neatplan-settings at layout.tsx:44, neatplan-sidebar-pinned at sidebar.tsx:52). Written on every change, read only when the URL is silent.
Server session / JWTRejected. Switching site would mutate the session and need a refresh round trip, two tabs could not hold two sites, and it would sit next to the real user.siteId claim that siteScopeWhere trusts for authorization - one confusion away from a privilege bug. Display preference does not belong in an auth token.

Back button. Use router.push, not replace. Changing site changes what the whole page is about, which is navigation-scale, and back-to-the-previous-site is what people reach for. The cost is history noise from rapid toggling. If that becomes annoying in practice, switch the pill row alone to replace and keep push on the popover - do not build debounce cleverness.

The URL is the single source of truth in the component: useSearchParams() reads it, fetchDashboardStats keys off it, and the effect at dashboard-overview.tsx:41 (currently []) gains the site value as a dependency so browser navigation refetches without any extra wiring.

5. API changes

The authorization rule

src/lib/authz.ts has resolveWriteSiteId (authz.ts:106) for writes but nothing equivalent for reads. Every read helper derives the site purely from the session and cannot express "this user asked for site X". That is the one new primitive needed.

// src/lib/authz.ts - new

export function resolveReadSiteId(
  user: SessionUser,
  requested?: string | null,
): string | null {
  // Pinned roles: the request is ignored entirely, exactly as
  // resolveWriteSiteId already does for writes (authz.ts:106-115).
  // NO_SITE keeps the fail-closed behaviour of siteScopeWhere.
  if (!canAccessAllSites(user.role)) return user.siteId ?? NO_SITE

  // All-sites roles: no request means no filter.
  if (!requested || requested === 'all') return null

  return requested
}

A MANAGER passing another site's id gets their own site's data. The requested value is never read on that branch, so there is no comparison to get wrong and no way for a crafted id to reach Prisma. This mirrors the write-side behaviour already in the codebase rather than inventing a second convention. A 403 was considered and rejected: the control does not render for a MANAGER, so a foreign id in the URL is either a stale bookmark or an attack, and returning their own correct data serves the first while telling the second nothing.

The returned id then feeds three shapers matching the three relationship shapes already in authz.ts. Each returns {} when the id is null, so an all-sites read is unchanged:

ShapeWhere clauseModelsMirrors
direct{ siteId }User, Room, EquipmentsiteScopeWhere (authz.ts:80)
nested{ [relation]: { siteId } }RoomSchedule via roomnestedSiteScopeWhere (authz.ts:90)
many-to-many{ sites: { some: { id } } }Schedulem2mSiteScopeWhere (authz.ts:118)

The two completion-log endpoints need the two-hop form the routes already hand-build, for example { roomSchedule: { room: { siteId } } } (completion-stats/route.ts:32, recent-activity/route.ts:28). No new mechanism, just the resolved id substituted for the session-derived one.

The four "consistency" endpoints could be filtered in the browser instead. Do not. Two reasons: the browser would download 109 rooms to display 55, and more importantly the KPI tiles would be computed by a different rule than the chart beside them. One rule - every dashboard fetch carries ?site= and the server decides - is the only version that cannot drift.

Every parameter is optional and additive. Omitting it reproduces today's behaviour exactly, so no existing caller breaks - which is what makes phase 1 of the build order shippable on its own.

Per-site views will not sum to "All sites", and that is correct. Two causes, both already in the code. Completion logs have a nullable roomScheduleId with onDelete: SetNull (prisma/schema.prisma:224-254), so a log whose schedule was deleted has no reachable site; recent-activity/route.ts:22-25 deliberately keeps those visible for OP and DIRECTOR. Selecting any specific site necessarily drops them. Separately, Room.siteId, Equipment.siteId, User.siteId and CleaningTask.siteId are all nullable (schema.prisma:23,88,124,143), so legacy null-site rows also appear only in the aggregate view. Do not "fix" this by making All sites the sum of the parts - that hides orphaned records. Document it, and consider a later "Unattributed" line item in the Audit page.

7. Build order

Each phase is independently shippable and leaves the app fully working. The APIs go first and stay invisible, so the UI phase can be reverted on its own without stranding anything.

  • Phase 0 - the helper. Add resolveReadSiteId and the three shapers to src/lib/authz.ts. Nothing calls them yet.
    Verify: unit tests alongside the existing ones in tests/unit/. Cases: OP with no request gives null; OP with an id gives that id; MANAGER with a foreign id gives their own; MANAGER with a null siteId gives NO_SITE; CLEANER same as MANAGER; unknown role treated as pinned.
  • Phase 1 - the three endpoints that have no alternative. Optional site param on /api/room-schedules, /api/admin/recent-activity and /api/admin/completion-stats. Two of the three need a request argument added to a zero-arg GET.
    Verify: curl matrix against the live server. OP with no param must return byte-identical output to today. OP with ?site=cms4sflah0000xg13gbyfb57f returns a strict subset. A MANAGER passing Maple's id gets their own site's rows.
  • Phase 2 - the remaining four endpoints. Same optional param on /api/rooms, /api/users, /api/admin/equipment, /api/schedules. Note /api/schedules uses the many-to-many shape, not siteId.
    Verify: same curl matrix, plus confirm the seven other pages that call these endpoints are unaffected when the param is absent.
  • Phase 3 - the control, inert. Build src/components/dashboard/site-filter.tsx using useThemeColors tokens (tabActiveBg, tabActiveText, tabInactiveBg, tabInactiveHoverBg, inputBorder - the same set the existing pickers at rooms/page.tsx:333-344 use). Render it in the header at dashboard-overview.tsx:121-134. Include the full role and count gating from sections 2 and 3. Selection changes nothing yet.

  • Phase 4 - wire it up.     Verify: Playwright. Select Maple, assert Total Rooms drops from 109 to 55 and the URL gains ?site=. Refresh, assert it holds. Back, assert it returns to all sites. Open the deep link in a fresh context, assert it lands scoped.
